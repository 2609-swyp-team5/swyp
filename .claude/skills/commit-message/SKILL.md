# 커밋 메시지 작성

이 저장소(swyp-project)의 커밋 컨벤션에 맞춰 커밋 메시지를 작성하는 스킬이다.
절대로 사용자의 명시적 확인 없이 `git commit`을 실행하지 않는다. 이 스킬의
결과물은 "커밋 메시지 초안"이며, 실제 커밋 실행은 사용자가 승인한 뒤에만 한다.

## 1. 변경 사항 파악

다음을 순서대로 실행해서 무엇이 바뀌었는지 파악한다.

```bash
git status
git diff --staged
git diff
```

- 스테이징된 변경(`git diff --staged`)이 있으면 그것을 커밋 대상으로 우선한다.
- 스테이징된 게 하나도 없고 unstaged 변경만 있다면, 그 변경 내용을 기준으로
  메시지를 작성하되 사용자에게 "스테이징된 변경이 없다"는 점을 알리고
  어떤 파일을 스테이징할지 먼저 확인한다. 사용자 승인 없이 임의로
  `git add -A`처럼 전체를 스테이징하지 않는다.
- 변경 사항이 서로 관련 없는 여러 주제(예: CI 설정 변경 + 프론트 기능 추가)를
  섞고 있다면, 하나의 커밋 메시지로 뭉뚱그리지 말고 커밋을 나누는 것을
  제안한다.

## 2. 코드 리뷰 관점 반영

커밋 메시지에 "무엇을 왜 바꿨는지"가 드러나야 하므로, 단순히 diff를 요약하는
것을 넘어 가벼운 코드 리뷰 관점으로 변경을 훑는다.

- 이번 대화에서 이미 `/code-review`(또는 ultrareview)를 실행한 적이 있다면
  그 결과(발견된 버그, 수정한 내용)를 메시지 작성에 반영한다.
- 아직 리뷰한 적이 없다면, diff를 훑어보면서 "이 변경이 버그 수정인지,
  기능 추가인지, 설정/도구 변경인지, 리팩터링인지"를 판단한다. 굳이
  `/code-review`를 새로 실행할 필요는 없다 — 커밋 메시지 작성에 필요한
  수준의 요약이면 충분하다.
- 여러 파일에 걸친 변경이라도 "왜"가 하나로 수렴하면(예: 백엔드/프론트 포맷팅
  도구 동시 도입) 하나의 커밋 메시지로 정리해도 된다.

## 3. 이 저장소의 커밋 컨벤션

`git log --oneline -20`으로 확인한 실제 컨벤션은 다음과 같다.

- 형식: `<type>: <한글 설명>` 한 줄. 본문(body)은 쓰지 않는다.
- `type`은 Conventional Commits 스타일: `feat`, `fix`, `test`, `refactor`,
  `docs`, `chore`, `style`, `perf` 등 변경 성격에 맞게 고른다.
- 설명은 한글로, 명령형/개조식으로 간결하게 쓴다. 예:
  - `feat: 프로젝트 초기 환경 구성`
  - `fix: CI 스크립트 수정`
  - `fix: 프론트 테스트시 폴더없으면 생략`
  - `test: CI 파이프라인 테스트`
- 제목 길이는 대략 50자 내외를 넘지 않도록 한다. 굳이 스코프(`fix(ci):`)를
  쓰지 않는 것이 기존 관례다.
- "무엇을 했는지"보다 이유가 명확히 드러나는 짧은 명사구/개조식 표현을
  선호한다 (기존 커밋들이 그런 스타일).

새로 작성하기 전에 `git log --oneline -20`을 다시 확인해서, 그 사이에
컨벤션이 바뀌지 않았는지 점검한다.

## 4. 결과 제시

1. 위 컨벤션에 맞는 커밋 메시지 후보를 1개(애매하면 최대 2~3개) 제시한다.
2. 변경이 여러 주제를 섞고 있다면 "커밋을 나누는 게 좋겠다"는 의견과 함께
   커밋별 메시지 후보를 나눠서 제시한다.
3. 사용자가 특정 메시지를 확정하거나 직접 커밋을 요청하면, 그때 아래처럼
   heredoc으로 커밋한다 (스테이징이 안 되어 있으면 먼저 스테이징 대상을
   확인한 뒤 `git add <파일들>`로 필요한 파일만 추가).

```bash
git commit -m "$(cat <<'EOF'
<확정된 커밋 메시지>
EOF
)"
```

4. 커밋 후 `git status`, `git log -1`로 정상적으로 커밋됐는지 확인한다.
